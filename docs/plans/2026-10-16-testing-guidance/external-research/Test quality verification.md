# Ask whether each test can fail first

The most reliable way to check tests after they are written is to ask, mechanically and with evidence, whether each test can fail. Holistic "is this a good test?" judgment comes second. The strongest evidence points in one direction. **80.2% of agent-authored test patches carry weak or no oracle signals** ([arXiv 2606.18168](https://arxiv.org/abs/2606.18168)). Agent commits add mocks more often than human commits (36% against 26%) ([Hora and Robbes, arXiv 2602.00409](https://arxiv.org/html/2602.00409v1)). No study validates an LLM judge for unit-test value. Deterministic detectors cover the "cannot fail" end of the problem well in Ruby and JS/TS and thinly in Python, and the most useful rules are often opt-in. Mutation testing is the only objective measure of "covered but not asserted" and of redundancy, but it costs real time. A redundancy finding needs a full test-by-mutant kill matrix and is still only a candidate, because suite-minimization studies report fault-detection loss anywhere from none to severe. Kent Beck's Test Desiderata and Google's guidance give a vocabulary for the judgment that remains: behavioral, structure-insensitive, specific, predictive. Industry precedent (Meta's TestGen-LLM, Google's mutation-in-review) never lets LLM judgment act alone; objective filters decide. For wb, this favors a test-auditor that runs explicit, stack-specific rule selections and planted-defect checks first, uses decomposed criteria with line evidence for the judgment layer, and proposes but never performs pruning. Prior work on how agents write tests is in [LLM test writing practices](LLM%20test%20writing%20practices.md). This report covers what happens after the tests exist.

## Beck's twelve properties name trade-offs, Google names the failures

Beck's Test Desiderata lists twelve properties a test may have, and states plainly that no test maximizes all of them ([testdesiderata.com](https://testdesiderata.com/)). Four of them carry most of the weight for deciding whether a test is worth keeping. **Behavioral**: "If the behavior changes, the test result should change." **Structure-insensitive**: "tests should not change their result if the structure of the code changes." **Specific**: "if a test fails, the cause of the failure should be obvious." **Predictive**: "if the tests all pass, then the code under test should be suitable for production." Beck frames the others as trade-offs. Predictive tests tend to be slower, and composability can make some conflicts go away ([testdesiderata.com](https://testdesiderata.com/)). So a test that gives up a property is not automatically defective. A rubric built on the desiderata should flag only trade-offs that buy nothing, such as a slow test that is no more predictive than a fast one. Several public agent skills already package "Test Desiderata review" as a code-review rubric ([skills.sh goblindegook/test-desiderata](https://skills.sh/goblindegook/skills/test-desiderata); [smithery eferro/test-desiderata](https://smithery.ai/skills/eferro/test-desiderata)). Their contents were not inspected, and **no study measures how consistently reviewers apply the desiderata**.

Google's *Software Engineering at Google* turns those properties into concrete failure definitions. A brittle test "fails in the face of an unrelated change to production code that does not introduce any real bugs." The ideal test "never needs to change unless the requirements of the system under test change." Tests should go through public APIs, prefer state over interactions, and test "each behavior" rather than each method ([SWE book ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)). On test doubles, the preference order is real implementation, then fake, then stub or mock. Mock-heavy suites "required constant effort to maintain while rarely finding bugs," and tests that overuse interaction verification are jokingly called **change-detector tests** ([SWE book ch. 13](https://abseil.io/resources/swe-book/html/ch13.html); [Google Testing Blog](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html)). Kent C. Dodds describes the same failure from the other side: implementation-detail tests produce false negatives on refactor and false positives when real behavior breaks ([kentcdodds.com](https://kentcdodds.com/blog/testing-implementation-details)). Empirically, developers mock dependencies that are hard to test and avoid mocking domain classes. Mocking also increases coupling between test and production code ([Spadini et al., MSR 2017](https://serg.ewi.tudelft.nl/publications/to-mock-or-not-to-mock-an-empirical-study-on-mocking-practices)). Agents diverge from humans here not only in mock volume but in the kind of double they use. **Fakes appear in 32% of agent repositories against 57% of non-agent ones** ([arXiv 2602.00409](https://arxiv.org/html/2602.00409v1)). That makes "a mock where a fake or real implementation exists" a specific signal for agent-written suites. The effect is small, though: Cliff's delta is 0.252 in the most active repositories and negligible elsewhere.

Together these sources support four verdict classes. **Remove** a test that cannot fail: no assertion, a tautology, only asserting that a mock was called, or asserting the framework's own behavior. **Rewrite** a change-detector or implementation-detail test. **Consolidate** duplicate tests of one behavior, or per-method tests that should be per-behavior. **Keep** a public-API behavior test with a specific oracle. This classification is a synthesis from Google and Dodds, not a published standard. No primary source was found that addresses trivial getter tests or snapshot overuse directly.

## Smell catalogs are detectable, but harm evidence ranks them unevenly

The tsDetect catalog at testsmells.org defines about 19 detectable smells, including Assertion Roulette, Conditional Test Logic, Empty Test, Unknown Test (no assertion), Redundant Assertion (always true or false), Sleepy Test, Mystery Guest and Lazy Test ([testsmells.org](https://testsmells.org/pages/testsmells.html)). The LLM-smell study used 21 ([arXiv 2410.10628](https://arxiv.org/abs/2410.10628)). LLM output is heavy in a few of them. Across 20,500 LLM-generated suites compared with 780,144 human-written ones, Magic Number Test and Assertion Roulette dominated ([arXiv 2410.10628](https://arxiv.org/abs/2410.10628)). Siddiq et al. found Magic Number Test and Lazy Test the most common ([arXiv 2305.00418](https://arxiv.org/abs/2305.00418), search-snippet summary).

**How common a smell is in LLM output does not tell you how harmful it is.** The harm evidence is mixed and secondary. Developers in a 2016 study generally did not recognize harmful smells, and Bavota et al. (2015) reported a significant negative effect on maintenance. Both are known here only through a later summary ([arXiv 2107.13902](https://arxiv.org/pdf/2107.13902)). In a severity study, 31 developers rated 301 smell instances. They put **Empty Test, Ignored Test and Conditional Test Logic** highest for maintenance impact, and Empty Test, Sleepy Test and Mystery Guest highest for refactoring priority ([arXiv 2107.13902](https://arxiv.org/pdf/2107.13902); authorship and venue not confirmed). The resulting split favors "can it fail?" smells (Unknown, Empty, Redundant Assertion, Ignored, swallowed exceptions) and flakiness smells (Sleepy Test, Mystery Guest, Resource Optimism). It argues against weighting the most frequent LLM smells. Lazy Test directly conflicts with Google's "test behaviors, not methods," and Magic Number Test has weak harm evidence. A rubric that flags them heavily would produce mostly noise.

The size rules are the clearest case of conflicting guidance. rubocop-rspec enables `RSpec/MultipleExpectations` with Max 1 and `RSpec/ExampleLength` with Max 5 by default. GitLab, the best-documented Rails team, instead says to "use `:aggregate_failures` when there is more than one expectation in a test" ([rubocop-rspec](https://docs.rubocop.org/rubocop-rspec/latest/cops_rspec.html); [GitLab best practices](https://docs.gitlab.com/development/testing_guide/best_practices/)). So an auditor should report against the project's own thresholds, not the defaults. Meszaros's xUnit catalog was not reachable in this research, so it is not cited.

Two gaps matter most for wb's audit. First, **no ecosystem has a detector for mocking volume**. RSpec is the partial exception for the most damaging case: `RSpec/SubjectStub`, `AnyInstance` and `MessageChain` catch stubbing the subject, global stubs, and stubbed chains. Everywhere else the lint rules check mock mechanics, such as `no-mocks-import` or Ruff's `PT008`, not whether the mocking is appropriate. The heuristics left for an auditor to compute or judge come from Google and Spadini: the subject or a value or domain class is mocked; non-state-changing calls are verified; only `have_received`/`toHaveBeenCalled` assertions are present; a cheap real implementation or fake exists but was not used. **No source gives a validated mocks-per-assertion threshold.** Second, **no linter can see a mirrored oracle**: an expected value computed with the production formula, the production hash, or the production serializer. Mutation testing or a planted defect can expose one, and so can a reviewer who checks where the expected value came from.

Coverage does not fill either gap. SimpleCov's own README says coverage "normally tells you whether a line ran, not what ran it" ([simplecov](https://raw.githubusercontent.com/simplecov-ruby/simplecov/main/README.md)). Mutation tools are now marketed explicitly as the check on AI-written tests ([mutant README](https://github.com/mbj/mutant)). mutant is license-gated for commercial use, though ($30 a month per developer). Some limits of incremental mutation are also documented. mutant's `--since` misses indirect effects ([mutant incremental](https://raw.githubusercontent.com/mbj/mutant/main/docs/incremental.md)). Stryker does not detect changes to dependencies, environment variables or snapshots ([Stryker](https://stryker-mutator.io/docs/stryker-js/incremental/)). PIT labels its history mode experimental. Sources disagree on whether Jest's obsolete snapshots fail a `--ci` run ([Jest issue mirror](https://gitlab.com/oss-integration1/jest/-/issues/12564)), so treat that behavior as unresolved.

## Redundancy and brittleness are suite-level questions that need history or a kill matrix

A single test file cannot show that a test is redundant. The rigorous measure uses mutation: a test adds no measured fault-detection value if every mutant it kills is also killed by other tests. Computing that needs the full test-by-mutant matrix. **PIT's default report records only the first killing test**, so later tests falsely look like they kill nothing. `-DoutputFormats=XML -DfullMutationMatrix=true` fixes this ([MutantReductionEvaluation](https://github.com/zhangpengNJU/MutantReductionEvaluation)). One user report says the full matrix breaks when combined with incremental analysis ([pitusers](https://groups.google.com/g/pitusers)). Stryker's per-mutant `killedBy` field is known here only from a secondary page flagged for injection risk ([tessl.io](https://tessl.io/registry/testland/mutant-survival-triage/files/references/tool-normalization.md)), so it is unverified. Coverage overlap, for example through coverage.py contexts, is cheaper. A study of Java projects found it **produces many false positives** unless mutation analysis backs it up ([reduction study](https://silicon-austria-labs.elsevierpure.com/en/publications/analyzing-the-reduction-of-test-suite-redundancy), snippet only).

Even with perfect matrices, deleting tests is risky. Minimization studies consistently remove about 70% of suite size, but fault-detection loss varies. Noemmer and Haas found about **12.5% average loss** ([Teamscale SWQD 2020](https://teamscale.com/hubfs/26978363/Publications/2020-test-suite-minimization-swqd.pdf?hsLang=en)). Jehan and Wotawa found none on the JavaScript programs they studied ([IEEE Access 2023](https://doaj.org/article/2c476261156943f588292e22db8300bd)). Older studies split between negligible and severe loss ([Zhang et al. ISSRE 2011](https://personal.utdallas.edu/~lxz144130/cs6301-readings/zhang-issre11.pdf)). TripRL's authors warn that detecting 100% of known faults "cannot guarantee strong fault detection ability for future unknown faults" ([arXiv 2408.13517](https://arxiv.org/pdf/2408.13517)). Google is the strongest industrial precedent. It surfaces **surviving mutants on changed lines during review**, capped per line and per review, and skips "arid" lines such as logging. It does not recommend deleting tests ([arXiv 2102.11378](https://arxiv.org/abs/2102.11378)). The industrial pattern is gap-finding, not pruning. Even rubocop-rspec's `RepeatedExampleGroupBody` comes with GitLab's caution to check coverage before deleting the duplicate ([GitLab](https://docs.gitlab.com/development/testing_guide/best_practices/)).

Brittleness shows up in git history. Mining same-commit test and production co-change is an established technique, but CHOSEN (2023) shows that such samples are noisy and need filtering ([SMU InK](https://ink.library.smu.edu.sg/sis_research/8280)). So raw co-change frequency is a weak signal. A sharper signal comes from the workflow itself. **A commit labeled structural (a behavior-preserving refactor) that still had to edit tests is a direct change-detector symptom.** This is an inference from Google's definition, not a published detector. Duplicated setup is a related signal. When one stub block is copied across many spec files and every request-shape change forces edits to all of them, the suite has the brittleness profile Google describes.

Flakiness needs repeated runs. Rerunning tests is the baseline method. Google's figures are that **about 1.5% of runs and about 16% of tests** show flakiness ([Google Testing Blog](https://testing.googleblog.com/2016/05/)). The deterministic workflow is a seeded random order, reproduction by seed, and minimization (`rspec --bisect`, pytest-randomly with `--randomly-seed`, Jest `--randomize --seed`). Repeat runs should target suspects only, because repeating a whole suite multiplies its runtime. GitLab is retiring in-process `rspec-retry` in favor of process-level retries and tracked quarantine ([gitlab#449030](https://gitlab.com/gitlab-org/gitlab/-/issues/449030)). So retry metadata in a suite indicates flakiness that is being masked.

## LLM judges are advisory: about 75–96% smell detection, with no validation for test value

LLMs detect test smells moderately well. Gemini-1.5 Pro reached **74–80%** in one 2025 comparison, but LLM refactoring sometimes introduced new smells, and GPT-4 and LLaMA often lowered coverage ([arXiv 2506.07594](https://arxiv.org/abs/2506.07594v1)). A four-agent setup with small models reached 96% detection pass@5 on five smell types ([arXiv 2504.07277](https://arxiv.org/html/2504.07277v2)). **No study measures how well an LLM agrees with developers on unit-test value, or evaluates LLM-driven deduplication or pruning.** The general literature on rubric judges warns against holistic scoring. Fine-grained rubric verification is noisy even for frontier models and worst on agentic coding. Majority voting helps, with diminishing returns ([RuVerBench, arXiv 2606.29920](https://arxiv.org/html/2606.29920v1)). Rubric wording alone predicts judge outputs above chance ([arXiv 2609.02942](https://arxiv.org/html/2609.02942v1)). High test-retest reliability can coexist with severe position bias ([arXiv 2606.19544](https://arxiv.org/pdf/2606.19544)). All three are known here from search snippets only. A "drop criteria below kappa 0.4" rule of thumb comes from a blog, not a standard ([Medium](https://medium.com/@adnanmasood/rubric-based-evals-llm-as-a-judge-methodologies-and-empirical-validation-in-domain-context-71936b989e80)).

Meta's TestGen-LLM shows how to use model output safely. A candidate test survives only if it builds, passes reliably, and adds coverage. **Only 25% of candidates survived those filters, and engineers accepted 73% of what reached them** ([arXiv 2402.09171](https://arxiv.org/abs/2402.09171v1)). Agents also delete or modify failing tests to get a pass ([ImpossibleBench, arXiv 2510.20270](https://arxiv.org/abs/2510.20270)). Together these make "LLM proposes, objective checks decide" the defensible policy for any consolidation or removal.

## What this implies for wb's rubric and auditor

This section is recommendation, not finding. The design points it builds on are [design.md](../design.md) D6 (verifier integrity), D7 (`test-quality` skill), D8 (`wb:test-auditor`), D10 (conventions and profile), the Data Model, and AC-6/AC-9. The audit evidence is [test-audit.md](../test-audit.md) W1–W6. One constraint shapes everything below. A recent check found that **W1 (hollow reds) and W2 (post-red edits) are invisible to a cold repository-plus-git audit, while W3–W5 are visible**. Those two weaknesses can only be caught with the per-task evidence D6 already plans: test-writer reports, red commits, and a diff against the task's starting commit. The cold `/wb:test-audit` mode cannot recover them. AC-6's example ("hollow reds or mirrored oracles (W1/W3)") and its "4 of 5 categories" bar should be read in that light. On a cold run, the reachable categories are W3, W4, W5 and W6.

## Conclusion

Most test-quality advice treats quality as a property of an individual test. The evidence here shows that the costly failures are often relational: a test that mirrors the code it checks, a stub block copied across eight files, a structural commit that forced test edits, or a test whose mutants other tests already kill. These relations are visible only through git history, a kill matrix, or a declared seam. That is why wb's design has an advantage most tools lack. Acceptance criteria with declared seams, red commits, and structural/behavioral commit discipline turn several judgment calls into near-mechanical comparisons. The flip side is that the cold `/wb:test-audit` will always be weaker than the in-plan auditor, and its acceptance bar should reflect that.

The largest open unknown is the auditor's own error rate. No published study measures LLM agreement with humans on test value. The calibration set wb can build from its own audit (labeled W3–W5 instances and clean controls) would be new evidence, not only a safeguard. Logging which deterministic rules fire, which planted defects survive, and which Remove proposals humans accept would show, within a few phases, which parts of the rubric earn their context cost.
