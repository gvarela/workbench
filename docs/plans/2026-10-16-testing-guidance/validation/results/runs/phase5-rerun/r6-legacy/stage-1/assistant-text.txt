### Implementation caveats
- `Decimal(12.25)` is exact because 12.25 is representable in binary. A value like 0.15 is stored as 0.1499999..., so `Decimal(0.15)` rounds half-up to 0.1, while `Decimal(str(0.15))` gives 0.2. The design says "convert through Decimal", but it does not say which constructor to use. That choice decides the result for non-binary-exact ties. Test inputs such as 12.25 work either way.
- `quantize(Decimal("0.1"), rounding=ROUND_HALF_UP)` always emits one decimal place. This produces the `5.0` problem for ints, and the design does not address it.

## Pattern Analysis: small in-place behavior change (WINDOW_DAYS and format_distance)

### Existing use of decimal, quantize, or rollout machinery
- A grep-equivalent read of every `.py` file found no `decimal`, `Decimal`, `quantize`, or `ROUND_*` anywhere. The only rounding is the built-in `round(km, 1)` at `rides/view_model.py:6`.

### Date-window and constant pattern (`rides/store.py`)
- `WINDOW_DAYS = 27` is at line 4. It is the only module-level constant in the package.
- `list_rides` (lines 7-11) computes `cutoff = today - timedelta(days=WINDOW_DAYS - 1)`. It filters with the inclusive check `cutoff <= r["date"] <= today` and sorts newest first.
- `WINDOW_DAYS` is used only in `list_rides`. `load_series` (lines 14-21) uses its own hard-coded values (`range(4)`, `7 * week`, `days=6`). It uses inclusive `start <= date <= end` windows, the same style as `list_rides`.
- Because of the `- 1`, the current 27-day window spans 27 calendar days including today. With a 27-day window and `TODAY = 2026-10-28`, the cutoff is 2026-10-02.
- `today` is always passed in as a parameter, never read from the clock. Callers pass it to `list_rides`, `load_series`, `render_rides_page` and `render_today_page`.

### format_distance (`rides/view_model.py:4-6`)
- Its docstring is: "Distance as a display string, rounded to one decimal, e.g. 12.3 km." It promises one decimal, but built-in `round` drops a trailing `.0`.
- The output is `f"{round(km, 1)} km"`. An int input gives `"5 km"`, since `round(5, 1)` stays an int. A float like `5.0` would give `"5.0 km"`.
- `round(12.25, 1)` gives 12.2, which is banker's rounding combined with binary float representation. The test at `tests/test_view_model.py:8-9` pins exactly this: `format_distance(12.25) == "12.2 km"`.
- That test will conflict with ROUND_HALF_UP, which gives 12.3. It encodes the old behavior.
- `test_keeps_a_whole_number_whole` (line 12-13) pins `format_distance(5) == "5 km"`. A Decimal quantize to `0.1` would produce "5.0 km" unless handled.

### Callers (`rides/views.py`)
- `render_rides_page` (lines 6-11) calls `list_rides(rides, today)` and `format_distance(r["km"])` at line 8.
- `render_today_page` (lines 14-17) calls `format_distance` at line 16. It does not use `list_rides`, because it filters `r["date"] == today` itself.
- So a `format_distance` change affects both pages, and a `WINDOW_DAYS` change affects only the rides page.
