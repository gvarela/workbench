## P2

- Verdict: PARTIALLY CONFIRMED (a conflict exists, but no public doc states "read only the part you need" as a rule; the strongest public evidence is a different one: the rule is mechanically unsatisfiable)
- Evidence:
  - Repo: CLAUDE.md:115 "3. **File Reading Protocol**: ALWAYS read files FULLY (no limit/offset) before analysis"; CLAUDE.md:186 "6. Read files fully before processing".
  - Mechanical conflict (public, <https://code.claude.com/docs/en/tools-reference.md>, "Read tool behavior"): "By default, Read returns the file from the start. When a whole-file read exceeds the token limit, Read returns the first page with a `PARTIAL view` notice that tells Claude how much of the file it received and how to read more with `offset` and `limit`." A large file therefore cannot be read fully without offset/limit, so "no limit/offset" contradicts the tool itself.
  - Public context-economy guidance points the same way as Claude's Read tool instruction, but it is not stated as a read-scope rule:
    - <https://code.claude.com/docs/en/best-practices.md>: "Claude's context window holds your entire conversation, including every message, every file Claude reads ... performance degrades as it fills." and "**The infinite exploration.** ... Claude reads hundreds of files, filling the context. > **Fix**: Scope investigations narrowly or use subagents".
    - <https://code.claude.com/docs/en/costs.md>: "Specific requests like 'add input validation to the login function in auth.ts' let Claude work efficiently with minimal file reads." and "Instead of Claude reading a 10,000-line log file to find errors, a hook can grep for `ERROR` and return only matching lines".
  - Counter-evidence: the public prompting guide (<https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices>, "Minimizing hallucinations in agentic coding") has a sample that says "If the user references a specific file, you MUST read the file before answering. Make sure to investigate and read relevant files BEFORE answering". That supports read-before-claiming, which is the repo rule's real purpose ("analysis on partial context produces placeholders", CLAUDE.md:148). It does not say whole versus partial. I found no public doc that says "always read whole files". I also found none that says "read only the needed part".
- Source quality: the original source was Claude's own Read tool description (non-public system/tool text: "When you already know which part of the file you need, only read that part"). A public equivalent in those words was **not** found. The public tools reference supports the narrower mechanical point.
- Correction: Grade the "read only what you need" rationale as Claude-internal. Rest the public case on two points. First, "no limit/offset" is impossible for files past the Read token limit, per the tools reference PARTIAL view note. Second, Claude Code's best-practices and costs docs treat file reads as context cost. Suggested fix: "Read every file you will make claims about, and read all of any file you are analyzing or changing (page through with offset/limit when Read returns a PARTIAL view); do not claim anything about unread code." That keeps the rule's anti-placeholder intent.

## P3

- Verdict: PARTIALLY CONFIRMED (the CAPS/CRITICAL/MUST part holds, with a nuance; the "think deeply/think very carefully is cruft" part is overstated and partly refuted)
- Evidence:
  - Aggressive language, confirmed (prompting guide): "If your prompts were designed to reduce undertriggering on tools or skills, these models may now overtrigger. The fix is to dial back any aggressive language. Where you might have said "CRITICAL: You MUST use this tool when...", you can use more normal prompting like "Use this tool when..."." And: "**Tune anti-laziness prompting:** If your prompts previously encouraged the model to be more thorough or use tools more aggressively, dial back that guidance." Also "Add context to improve performance": "**Less effective:** NEVER use ellipses / **More effective:** Your response will be read aloud by a text-to-speech engine, so never use ellipses ...". Note that the public guidance is framed around the 4.5/4.6 generation and tool overtriggering, not as a blanket ban.
  - Emphasis nuance (<https://code.claude.com/docs/en/best-practices.md>): "If Claude keeps skipping one instruction, add emphasis such as "IMPORTANT" to that line alone. If you emphasize many lines, none of them stands out." Emphasis is endorsed when targeted; volume is the problem.
  - Think keywords (<https://code.claude.com/docs/en/model-config.md>, "Use ultrathink for one-off deep reasoning"): "Include `ultrathink` anywhere in your prompt to request deeper reasoning on that turn without changing your session effort setting. Claude Code recognizes the keyword and adds an in-context instruction. The effort level sent to the API is unchanged. Claude Code passes other phrases such as "think", "think hard", and "think more" through as ordinary prompt text and doesn't recognize them as keywords." So "think deeply" and "think very carefully" trigger nothing in the harness. `ultrathink` itself adds only an in-context instruction; it is not effort configuration. Calling ultrathink "configuration" is wrong: it is a harness-injected prompt, and effort is unchanged.
  - **Counter-evidence, which refutes "think prose is cruft":**
    - Prompting guide, "Leverage thinking": "**Prefer general instructions over prescriptive steps.** A prompt like "think thoroughly" often produces better reasoning than a hand-written step-by-step plan."
    - Same page: "The triggering behavior for adaptive thinking is promptable."
    - model-config: "If you want Claude to think more or less often than the current level produces, you can say so directly in your prompt or in `CLAUDE.md`; the model responds to that guidance within its effort setting."
    - Opus 4.7 guidance on the effort page: "If you must keep effort low for latency, add targeted guidance like "This task involves multistep reasoning. Think carefully before responding.""
    - Where public guidance does say effort beats prompting, it is about reducing thinking. Sonnet 5.5 migration (bundled L2177, mirrored publicly): "a system-prompt request to think less has almost no effect at those levels". Opus 5.5 (bundled L2014): "lower the effort level before adding "think less" instructions".
  - Repo state: no shipped file still contains think-deeply/ultrathink. `grep -rniE 'think deeply|think very carefully|think hard|ultrathink|think carefully' plugin` finds only plugin/scripts/README.md:59 (a lint-rule justification). The remaining uses are in docs/product-research-claude-desktop.md:77,88,167 and in historical plan docs. The repo's 2026-06-09 research.md:31 had called these "extended-thinking budget triggers in Claude Code". That was true of older Claude Code tiers, but model-config now documents it as not true.
- Source quality: the original sources were the bundled prompt-audit.md and a subagent report (both non-public). The public prompting guide covers the aggressive-language half. For the thinking half, the public docs contradict the claim: effort is the primary depth control, and prose remains a legitimate, documented steering lever.
- Correction: Revised claim: "Volume emphasis (CAPS/CRITICAL/MUST across many lines, repeated restatements) is dated. Current guidance is to dial back aggressive language, give the reason, and emphasize at most one line. 'Think deeply/think very carefully' triggers no Claude Code mechanism; only `ultrathink` is recognized, and it adds an in-context instruction without changing effort. Such prose is not cruft, because thinking is documented as promptable within the effort level. It is redundant where effort is set appropriately, and effort is the primary control. Bare, object-less 'think deeply' adds little; 'think thoroughly about X' is documented as useful." Drop the phrase "ultrathink keyword is configuration".

## P5

- Verdict: PARTIALLY CONFIRMED (the memory is quoted accurately, but it supports only "louder wording does not fix a trap"; it does not support "wording doesn't enforce waiting" in general, and the trial didn't exercise the harness at all)
- Evidence:
  - Memory text, verbatim (session hook stdout, "wb-barrier-volume-not-discriminator"): "wb blind trial 2026-09-05 (fable-5-1-rebaseline Phase 2, 36 Sonnet runs): barrier wording volume does not hold a wait-for-all gate. On a trap with 2/3 agent reports back and the 3rd streaming a near-complete partial, Sonnet synthesized anyway under both the triple-⛔ STOP! line (WAIT 0/3) and a single-⛔ line with a stated reason (WAIT 1/3). Positive/negative fixtures were 3/3 under both. Implication: don't spend on louder barrier text; a partial-report gate needs a harness mechanism or explicit async-spawn semantics."
  - Primary record: docs/plans/2026-09-01-fable-5-1-rebaseline/trials/2026-09-05-blind-trials.md. Method: "Fresh-context Sonnet subagents (general-purpose, told not to use tools), given only the verbatim instruction excerpt plus a synthesized fixture. 3 fixtures ... x 3 trials x 2 wordings". The Set A table shows negative (1/3 returned) "WAIT 3/3" under both wordings.
  - Weaknesses:
    - (a) n=3 per cell. 0/3 versus 1/3 is noise, and the positive/negative cells cannot discriminate either.
    - (b) Only Sonnet was tested, with no tools and a text-described scenario. That measures a model's stated decision about a fictional situation, not what happens in Claude Code, where a partially streamed report is never delivered as a returned result.
    - (c) The negative fixture (1/3 returned) was WAIT 3/3 under both wordings. Wording did produce waiting in the clear case, so "wording doesn't enforce waiting" in general is contradicted by the repo's own data. The failure is specific to the ambiguous near-complete trap, where the model judged the missing part "supplementary".
    - (d) The trimmed wording did no worse: "trimmed >= baseline holds on all three".
  - CLAUDE.md:151 and :182 (single ⛔ with a stated reason) match public guidance. See the prompting guide's "Add context to improve performance" ("Providing context or motivation behind your instructions ... can help Claude better understand your goals") and the aggressive-language passage quoted in P3. That part of the claim is confirmed.
- Source quality: bd memory (repo-recorded experiment). The primary trial file exists and matches the memory. It is not public and has small n.
- Correction: "The single-⛔-plus-reason barrier matches current prompting guidance. A small repo trial (Sonnet, no tools, n=3 per cell) found that neither loud nor plain wording held the gate in one ambiguous trap (a near-complete partial third report). Both wordings held it when 1/3 had returned. Louder text is therefore not a fix for edge cases. Reliable waiting has to come from how agents are spawned (foreground Agent calls return only when the subagent finishes; see M3), not from barrier volume. The trial did not test the harness." Don't generalize to "wording doesn't enforce waiting".

## P6

- Verdict: PARTIALLY CONFIRMED / REFRAMED. "Start at medium" is public API guidance for Sonnet 5.5, and Claude Code separately defaults Sonnet 5.5 to medium. The more important finding is that the repo's per-spawn `effort: xhigh` likely does nothing.
- Evidence:
  - API versus Claude Code: API default for Sonnet 5.5 is `high` (effort page: "`high` is the default on the Claude API"). Claude Code default for Sonnet 5.5 is `medium` (model-config: "Opus 5.5 and Sonnet 5.5 default to `medium`"). The "start with medium for agentic coding" advice is API guidance, and it coincides with Claude Code's default. Claude Code passes effort through to the API: "Effort levels control adaptive reasoning" and links the platform effort page. There is no evidence that Claude Code's xhigh differs from API xhigh, except the fallback on models without xhigh.
  - How subagent effort is set (<https://code.claude.com/docs/en/sub-agents.md>, frontmatter table): "`effort` | No | Effort level when this subagent is active. Overrides the session effort level. Default: inherits from session." The per-invocation override the doc lists is `model` only: "When Claude invokes a subagent, it can also pass a `model` parameter for that specific invocation." The Agent tool schema in this 2.1.285 session has `description, isolation, model, prompt, subagent_type` and no effort parameter.
  - Repo: plugin/agents/task-worker.md frontmatter has no `effort:` (only name, description, tools, skills, maxTurns: 60). Yet plugin/skills/implement/SKILL.md:199 tells the coordinator to "set `effort: xhigh`" when spawning, and plugin/skills/implement/sub-agent-prompts.md:116 says "fable model override at effort: high". Per the docs, the coordinator has no spawn-time mechanism to do this. Workers inherit the session's effort: medium if the coordinator runs Opus 5.5 at its default. At most, the instruction could leak into the prompt text as prose.
- Source quality: public Claude Code docs, plus direct observation of this session's Agent tool schema (harness-internal, consistent with the docs).
- Correction: Fold P6 into P1 and add the following. "The `effort: xhigh` per-spawn instruction in implement/SKILL.md:199 (and 'effort: high' for fable in sub-agent-prompts.md:116) has no documented mechanism. The Agent tool takes a per-invocation `model` but not `effort`, and task-worker.md sets no `effort`, so workers inherit the session's effort. To control worker effort, set `effort:` in task-worker.md frontmatter (one level for all tiers), or rely on the session level." Before stating this as final, verify empirically with `/tasks` (per sub-agents doc, it shows effort only when the definition sets it).
