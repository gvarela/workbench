# Changelog

All notable changes to the wb plugin. Versions are release cuts — installers receive a version only when it's bumped here AND they run `claude plugin update wb@gvarela-workbench`. See [RELEASING.md](RELEASING.md) for the process.

## [Unreleased]

Testing guidance: plans state what "done" means as acceptance criteria, a separate agent writes every test, and the verifier and phase checkpoints check that the tests can fail. This ships as 5.0.0. Plan: `docs/plans/2026-10-16-testing-guidance/`.

### ⚠️ Breaking

- **`task-worker` no longer edits tests, and no longer spawns anything.** It never creates, edits, or deletes a test file. `wb:test-writer` writes the task's tests before the worker starts, and a worker that needs another test stops and returns a `needs test:` block for the coordinator to act on. `/wb:implement_inline` follows the same rule.
- **Phase checkpoints can block.** A criterion the prover disproves by running the product, an unexplained deviation from the plan, and a deterministic failure in a test the phase changed each hold the go-ahead. A test gap whose fix changes tests only is closed without asking and listed under "Decisions I made for you"; what is left needs your answer by name (`fix: P1`, `accept: D1`). Judgment-only findings stay advisory, and tests the phase did not change never block.
- **Plans carry more.** `create_research` requires a Testing Conventions section in research.md. `create_design` replaces the Functional Requirements checklist with Acceptance Criteria (Given/When/Then, a real example, where it is observed, and the seam where an external service or LLM is involved) and adds a Harness Decisions table. `create_tasks` adds outer-test steps, harness tasks, and criterion citations.
- **Plans without acceptance criteria still run, with outer tests skipped.** A plan whose design.md has no Acceptance Criteria section (anything created before 5.0.0) is treated as having no criteria: `implement` and `implement_inline` say "plan predates 5.0.0", write no outer tests, and create no `red(AC-n)` commits. What does change for those plans: workers still cannot edit tests, inner tests go through `wb:test-writer`, the verifier still checks test integrity against the starting commit, and checkpoints run the phase test review and block on deterministic failures.
- **The verifier is stricter.** An undeclared test change, a non-identical outer test, or a test that does not protect its criterion (a planted defect that breaks what the criterion forbids survives) is a FAIL, never "minor".
- **`/wb:validate_execution` renamed to `/wb:validate_phase <dir> [phase|all]`**, with no alias. With a phase number it runs `wb:phase-verifier` and `wb:test-reviewer` on that phase; with `all` (the default once every phase milestone is closed) it runs a phase verifier per phase, a review of the whole plan's tests, and writes the Intent verdicts to the README. Its four custom validation agents are gone; automated verification runs once per run.
- **Checkpoints can also hold on a deviation.** Each unexplained deviation the phase verifier finds (a planned change missing, a change no task covers) needs your answer by name: accept, fix, or plan defect.

### Added

- **`/wb:review_diff`**, a dynamic workflow that reviews a branch cold before its pull request. Four `wb:diff-reviewer` agents read the change without the plan, one lens each; findings with one root cause are merged; a skeptic traces each from a real entry point before it counts. It edits nothing and runs only when you ask. Needs a Claude Code version with dynamic workflows.
- **`wb:judge`** (Fable, `high`; edits nothing): before a run stops to ask you anything other than a checkpoint's go-ahead, the judge reads the verifier's records, the criterion, and the diff itself, and returns one of four outcomes. **Repair**: a record or a link is missing, and the run fixes it and goes on. **Settle**: a call about tests inside stated limits (a finding outside its criterion is a follow-up; a literal reading of an aim whose purpose is met; a deviation an existing record explains; one more fix attempt on a test gap when the code is correct), recorded as `judged:` and listed for you with how to reverse it. **Recheck**: a fresh verification of one finding. **Person**: the question is yours, and the judge writes it as what would go wrong in the product, with the real choices. It never turns a failure into a pass, waives an integrity finding, changes what a criterion means, accepts lost coverage, or decides product behavior. `create_design` also runs it once before asking for approval, to list what the approval would pass in silence.
- **`wb:prover`** (Opus, `high`) runs the product at each acceptance criterion's boundary at every `implement` and `implement_inline` checkpoint, and in `validate_phase`, with the test review and the phase verifier. It works from the criterion, states what it expects before reading the implementation, uses the product's own entry point (the command, the request, the page), and reports each criterion and each manual check as proven, disproven, or could not prove, with the commands it ran and the output it saw. It edits nothing, stays local (no paid or external call unless the testing profile's `## Proof` section grants it), and posts its report on the phase milestone as a `proof` record. Passing tests show the tests pass; this shows the product doing what the criterion says.
- **`wb:test-writer`** writes every test, in four modes: an outer test per criterion, committed as `red(AC-n): ...` before any code; the task's own tests, before its worker runs; a test a worker asks for; and a rewrite of an outer test, with the evidence the proof rule needs. It reports the assertion failure for each.
- **`wb:test-reviewer`** (Opus) reviews a phase's tests with plan context: criteria, red commits, integrity findings. It runs at every `implement` and `implement_inline` checkpoint and in `validate_phase`, and plants defects only in a disposable copy.
- **`wb:phase-verifier`** (Opus, `high`) runs at every `implement` and `implement_inline` checkpoint, in parallel with the test review, and in `validate_phase`. It changes nothing but its own report, which it posts on the phase milestone, and reports planned changes missing from the phase diff, changes no task covers, earlier phases' tests the phase changed again, and progress toward each README Intent statement, so a gap costs one phase instead of being found after later phases built on it.
- **Automatic final verdicts**: the final phase's checkpoint writes a verdict per Intent statement (`→ PASS`, `→ FAIL`, `→ DEFERRED`) beside each README statement from the phase verifier's evidence, with no extra agent; a manual check's verdict waits on your reply. The rules live in `plugin/docs/reference/intent-verdicts.md`, shared with `validate_phase all`.
- **`create_tasks` Design Coverage**: before any beads issue is created, every design.md scope item and Success Metric is mapped to a task or a stated deferral in a Design Coverage table; you decide each one no task delivers (add a task, defer it, or drop it). The phase verifier reads the table.
- **`wb:test-auditor`** (Opus) audits one area of a repository cold, read-only.
- **`test-quality` skill**: the shared rubric the writer, verifier, reviewer, and auditor all read. It asks "can this test fail?" first, then checks behavioral, structure-insensitive, specific, and predictive properties. Each finding gets a Remove, Rewrite, or Consolidate verdict with file:line evidence and a proof.
- **`/wb:test-audit`**: a cold, read-only audit of a repository or directory. It triages first (the project's own detectors and heuristics rank tests; auditors inspect the top candidates), and before spawning it states the scope, the auditor count, and a cost class, asking you to confirm or narrow on large repositories. It deletes and edits nothing.
- **`/wb:testing-profile`**: drafts `.claude/wb/testing.md` (stack, commands, levels, seams, choices) and writes only on your confirmation. It recommends gaps against what the flow relies on (a harness per boundary, seams, unenabled lint rules, a mutation tool); you adopt, record as a choice, or decide later. If you do not control the repository's tooling, it suggests no tooling.
- **`plugin/scripts/test-integrity`**: a stack-neutral git script that reports changed test files, outer tests that differ from their red commit, added skip or focus markers, deleted tests, and test changes no report declares. `--plan-start <sha>` adds `earlier_phase_tests`: test files an earlier phase changed that this phase changes again. `--declared-path <path>` (repeatable) and `--declared-none` pass the declared files as arguments, so the agents need no list file; agents run each shell step as one plain command, which permission rules allow.
- **Optional `wb-defects` plugin 0.1.0**, in the same marketplace (`claude plugin install wb-defects@gvarela-workbench`): its `bin/wb-plant-defect` plants one defect per call in a disposable copy (setup, baseline, run, teardown), running only the guarding test file, with a literal find-and-replace break, a required control break per target and test file, timeouts relative to a baseline run, `--test-file <path>=@<commit>` or `=-` to run another version of a test, and JSON output carrying the blob hashes of the target and tests. The test command comes only from the `## Defect sandbox` section of `.claude/wb/testing.md` (or detection, reported as a guess), runs without a shell; the runner runs no setup commands. A worktree is the general path; a load-time swap of the one mutated file speeds up Python, Node, Ruby, and Go, and a persistent sandbox serves expensive environments. Allow it with `Bash(wb-plant-defect *)`. Allowing the wb-defects runner means trusting everything in the repository as code you'd run — its tests and its .claude/wb/testing.md profile — just as allowing its test runner does. As defence in depth it rejects known shells, inline-code flags, and launchers that reach beyond the repository (containers, remote hosts), runs no setup commands, and edits only a copy; a repository script can still run whatever it contains. The runner is not part of wb, which stays an orchestrator, and the plugin cannot be installed on claude.ai or in Cowork because it ships a `bin/` directory. See `wb-defects/README.md`.
- **Defect ledger**: `task-verifier`'s report lists every planted defect (test, target, both blobs, kind and location, outcome, control) in its own `defect ledger:` comment, posted before the `verification report:` comment and split into numbered parts when long, so later checks can see what was already checked on which code and a long ledger cannot push the report past the Bash tool's size limit.
- **`red(AC-n)` commits** preserve each outer test's failing state before implementation starts.
- **Red/green evidence in beads**: the outer-test step closes with the red commit and its assertion line, test-writer reports become comments on their task, and findings that outlive a checkpoint become linked issues. Resume, the verifiers, the reviewer, and `validate_phase` read them from there.

### Changed

- **Test review is proportionate** (from a run where about 12 lines of production code grew about 620 lines of tests over four hours of review rounds). One test owns each behavior: a criterion's outer test must catch a break of the criterion, and any other test must catch the break its own report names; a lower-level test that misses a break the outer test catches is no longer a failure. A checkpoint test gap gets one fix and one confirming review of that fix (`Confirm:`), and anything new is a follow-up. Planted defects are breaks a person might make, each kind planted once: not one per member of a set the code handles in one branch, and not the same break again at each layer. The rubric asks for a decision to be tested at the layer that makes it, with one representative per set of inputs treated alike. The checkpoint report shows lines of tests against lines of code.
- **Lint runs where it is cheap, and no longer reaches the test-integrity checks** (from runs where a style fix to an outer test after its red commit cost a full proof: 98 planted defects for a change of quote style in one, about an hour for one lint comment in another). `wb:test-writer` and `wb:task-worker` run the repository's format and lint commands on the files they touch before they report, so an outer test is clean before it is committed red. The coordinator runs them again before each verification and sends a failure back to its author, and lints the files a task will touch first, giving a file that already fails its own structural commit. A style failure is never a verifier finding about tests. The commands live in a `## Checks` section of `.claude/wb/profile.md`. `test-integrity` recognizes a change of lint directive comments only as mechanical (`lint-directive`), alongside whitespace and import re-sorts.
- **wb offers a format-on-write hook; it does not ship one.** When `/wb:implement` finds a format command in the profile's Checks section and the repository has no hook that runs it, it offers once to add a `PostToolUse` entry to the repository's `.claude/settings.json` that formats each file an agent writes. You see the exact entry and decide; it is never added unattended. Formatter only: lint stays with the author and the coordinator. See `plugin/docs/reference/format-on-write.md`.
- **A test gap costs fewer rounds** (from a run where a one-line change took four verifications because its outer test was strengthened one instance at a time). A fix the verifier checked against its planted defects is now passed to `wb:test-writer` word for word and applied as written, where it used to be "a starting point". And when a failed task's only finding is its outer test and its code is correct, the verification of the rewrite settles that task too, in the same run, so a second verifier no longer plants the same defects on the same code.
- **`wb:task-verifier` runs at `medium` effort, down from `high`.** It was half of all agent time in recent runs. On two sets of blind trials with seeded test-integrity defects it caught the same 12 of 12 at both levels, with no more false alarms, in 26 to 44 percent less time. The other reviewers are unchanged.
- **`/wb:create_design` runs as three passes: product, technical, program.** One combined discussion tended to settle one kind of question and call the design done. It now proposes which passes apply, from your Intent and the research, and you confirm; each pass asks only what the documents leave open and closes before the next begins. New questions: what a person sees and does and how the UI works (product); what the design relies on outside the repository and how it runs in production (technical); the contract of anything one task builds and another calls, and which existing patterns to follow (program). design.md records each layer as open, closed, or skipped with its reason, so running the command again resumes at the first open one, in a fresh session if you like.
- **`/wb:explore_design` hands its decisions to the design passes by layer.** It says whether each decision is a product, technical, or program one, flags a technical decision that rests on an unanswered product question, records what it settled for each layer, and adds its thoughts docs and any mockups to the README's Existing Material list. `/wb:create_design` opens each pass with what exploration settled and asks only the rest; before, it used the record only for the approach.
- **Conflicting guidance is settled at design, anywhere it appears.** Research records where the code does one thing two ways and any stated rule about it, both sides. One order of authority decides (your decision for the plan, a standing rule, the prevailing pattern nearby, the rest of the repository): a stated rule wins for new code without asking, and existing code that breaks it is left alone. What that leaves open is put to you in the program pass, and your answer can be recorded in a new `.claude/wb/profile.md` as a guideline to follow, to ask each time, or to follow with an exception. The testing rubric no longer says to follow the code over a stated rule. `.claude/wb/testing.md` is unchanged.
- **A design reaches the build wherever it came from.** `/wb:create_project` asks once whether anything is already designed or decided and starts an Existing Material list in the README. `/wb:create_design` reads it, finds what it lacks (wb's `mockups/` folder, files or a link handed over from elsewhere), and adds to it on your yes. For each screen the plan touches, the whole design is in scope until you say otherwise, and you approve one scope list: built to the design, left out with reasons, and touched but not designed, where you choose how each gap is handled. `/wb:create_tasks` maps each to the task that builds it. Before, the only link from a mockup to the build was saying "finalize" during mockup iteration.
- **Outer tests change on proof, not on your sanction.** An outer test changes after its red commit only through a rewrite task that `wb:test-writer` carries out, and the change lands when the task verifier's report shows three things: the criterion's text is unchanged; nothing the red-commit version caught is lost (the change is mechanical, or name only for a rename the design states, or a differential run shows every original case still caught); and no added assertion checks more than the criterion says. It is recorded as `rewrite:` and listed under "Decisions I made for you". When a case would be lost, when an added check goes beyond the criterion, or when no defect runner can run the differential, the decision is yours. The delegations (`delegate: test upkeep` and its three parts), R-numbered proposals, and sanction by name are gone; `not claimed:` remains, written only on your reply.
- **The instructions are smaller and read on demand.** The implement skill is 14,767 characters (was 46,417), so the whole loop survives a context compaction, and its 94,000-character reference file is six playbooks, each read only when its trigger fires. `task-verifier` is 19,035 characters (was 49,604), with its rewrite checks in a separate file read only for a rewrite task; `implement_inline` is 10,610 (was 45,356) and shares implement's playbooks. Instruction text across the plugin is about 749,000 characters, against 848,000 before, with three agents and a workflow added.
- **Each phase is best run in a fresh session.** The checkpoint report recommends it: a new session starts with a clean context and a single plugin version.
- **A record-keeping slip no longer stops a run** (from trial runs where a forgotten tracker link halted one run twice, for 6 and 10 hours, and a report that was never posted cost two stops). `wb-records` gains four commands: `put` posts any text as one comment and confirms it in the same call, printing the comment id that task-worker and `wb:test-writer` now return; `have` lets the coordinator check those ids before the verifier runs; `file` creates an issue with its `discovered-from` link and confirms the link; `link` adds a missing one. The task verifier reports a missing link on a Record gaps line that never fails the task, and the coordinator repairs it. A test change with no report is still an integrity finding.
- **The tree fingerprint works on a repository with a large dependency directory.** An ignored directory over 20,000 files or 500 MiB is fingerprinted by each file's path, size, and modification time and named in `metadata_dirs`, where it used to error on every verification. That catches a file added, removed, resized, or rewritten, not a same-size rewrite that restores the old modification time.
- **Checkpoints show proof, and the manual list is what could not be proven.** Each delivered criterion in the checkpoint report carries the prover's result. A disproven criterion holds the go-ahead as P1, P2, ..., answered `fix: P1` (a task through the normal loop, with its test through `wb:test-writer`) or `accept: P1`. "Manual checks" becomes "Left for you to check": only the criteria and manual checks the prover could not prove, each with its reason and steps. The coordinator never runs those checks in the prover's place. `create_design` criteria gain a `Proven by:` line, and `/wb:testing-profile` drafts a `## Proof` section (how to start the product, where it listens, how to place example data, which side effects are allowed). Plans without the line still get proved, from Observed at.
- **Checkpoint decisions you can evaluate.** Each item that reaches you leads with what would go wrong in the product, as one concrete example, and offers the choices that are real. Replies name the id and the choice (`fix: P1`), never file paths or commits. A choice you could not tell apart by anything you would see in the product is not asked: it lands on proof or is settled by the judge, and is listed under "Decisions I made for you" with how to reverse it.
- **`task-verifier`** runs `test-integrity` first, plants defects against the tests that guard cited criteria, and names the smallest realistic regression for each criterion. Every FAIL cites file:line and carries proof (a counterexample or a surviving planted defect); pattern rules only prompt that check.
- **`implement` and `implement_inline`**: the coordinator (or inline session) has the tests written first, passes the verifier its integrity inputs, runs the test review, the phase verifier, and the prover before each go-ahead, and records evidence in beads. A failed verification gets one automatic fix; after that the judge decides whether one more attempt is warranted or the question is yours.
- **Fewer repeated defect checks**: the phase test review skips a defect a verifier's ledger already shows on unchanged code (same target and test blobs) and plants only for uncovered tests, outer tests, other forms of a caught defect, and false-failure probes, reporting the skipped count; `/wb:implement_inline` has no ledger and plants as before. A re-verification plants only for the FAIL's class, plus every ledger line whose target or test blob the fix changed, which it never skips. Defects run against the guarding test files only, and a mutation tool is never re-run on a module unchanged since its last run.
- **Defect-check routes**: `task-verifier`, `test-reviewer`, `test-writer`, and the `/wb:implement_inline` session take the first route that can run, in order: `wb-plant-defect` when it is on the PATH; the repository's own mutation tool, only when `.claude/wb/testing.md` names a recognized one (mutmut, Stryker, PIT, cargo-mutants, mutant, or gremlins) with its exact command, scoped to the changed files with survivors judged against the cited criteria, under normal permission prompts and never installed or fetched; otherwise Not Run ("no defect runner: install the wb-defects plugin or configure a recognized mutation tool in .claude/wb/testing.md"), judged by reading. There is no hand-built worktree route. A rewrite's differential needs `wb-plant-defect`. The ledger, the reviewer's skip rule, targeted re-verification, guarding-tests-only runs, and Not Run counts apply on every route, and each report names the route that ran. The routes live in `plugin/docs/reference/non-interactive-shell.md` under "Planted defects".
- **Gates calibrated to block on cheating, not on imperfect tests** (from a trial run where 42% of task verifications failed, almost all on correct code, without one catching a worker cheating). What a worker could do to bend a test green still fails and still reaches you: a mirrored oracle, a loosened assertion with proof, a vacuous test, a skipped or deleted guard, an undeclared test change, and an outer test changed after red. Workers still never edit tests, and a general go-ahead still answers nothing. What changed:
  - **Protection FAILs track the criterion.** A planted defect fails a task only when its break violates the cited criterion's statement or an example; survivors outside it (future refactors, adjacent behavior) are filed as follow-ups.
  - **Scoped re-verification.** A re-verification plants for the failure's class and, always, every ledger line whose code or test changed; new survivors outside the class become follow-ups, and the phase test review plants the rest at the checkpoint.
  - **Mechanical test changes clear with a note.** `task-verifier` and the inline test review pass `test-integrity --allow-mechanical`; a test file whose whole change is an import re-sort (only plain top-of-file import lines moved) or a whitespace change, read and confirmed, is cleared rather than failed as undeclared. Before the verifier runs, the coordinator confirms each changed test file has its report.
  - **Rewrite differentials are finite.** A rewrite keeps every case on shapes present in the repository or named in the criterion's examples; other shapes go on a written "Not claimed" list in the test and the report, each entry citing the repository search that shows the shape is absent, which the verifier repeats. After the second lost-coverage round the halt recommends writing the remaining limits down, and accepting lost coverage stays your decision, by a reply that names the cases.
  - **Decisions are batched.** One pending-decisions ledger: each decision is asked in full once, later messages carry a one-line reminder, a reply can name a set (`acknowledge: T1-T3`, `accept: D1-D4`) that covers only ids still pending and shown in full earlier (a set with a gap, an answered or unseen id, or mixed kinds is not acted on), and conflicts in the plan's product wording are raised before the phase starts, not mid-task. Rules in `plugin/docs/reference/writing-for-the-user.md`.
- **Unattended mode and fewer waits** (from two unattended runs, one taking a whole plan to production and one running 5h38m with no input: calibration held, with real bugs caught and no cheating, but with no defined mode both coordinators improvised authority, and environment friction corrupted evidence). The coordinator wants green, so it must not grant itself decisions that are yours:
  - **`run unattended`**, named in your own message, starts unattended mode for `/wb:implement` and `/wb:implement_inline`; your next message ends it, and it is recorded verbatim. The run may only edit what a ready planned task names (or its worker and test-writer produce), run that task's checks, make local task commits, and update beads; anything else parks the task. A checkpoint is recorded without you (`checkpoint-auto:`, copying the reviewer's and phase verifier's lines verbatim and naming every task's verification-report manifest) only when nothing blocks, nothing deviates, every phase task has a manifest-checked verification report, and nothing is pending; its milestone stays open awaiting your manual checks. A checkpoint with anything to decide (an additive strengthening included) gets a `deferred:` ledger and stops the run. A halted task, a production-defect re-verification FAIL among them, is parked in a private commit at an immutable `refs/wb/parked/<task>/<nonce>` (never `git stash`, and never when anything is already staged), and only tasks independent of it in beads, files, and criteria go on; one further fix attempt the judge settles is the only extra attempt. Never in unattended mode: amending design or tasks decisions, skipping a verifier, parallel tasks, production stubs, unplanned migrations or shared-resource changes, deploys, pushes or history rewrites, deleting data or branches, paid runs or side-effecting network calls, CI, `.claude/`, git hook or config, plugin or MCP changes, package or lockfile changes outside a task, editing `.claude/wb/testing.md`, or any decision attended mode reserves for you. The run ends with one report holding every deferred item in full, with restore steps for each park.
  - **Replies**: every reply to a decision is recorded verbatim as a `user reply:` record, never paraphrased, and each pending item a reply does not name is echoed back ("P2 not answered — reply fix: P2 or accept: P2"), in every mode.
  - **Posting survives the worktree-isolation guard**: `task-worker`, `wb:test-writer`, and the coordinator write text with the Write tool to a unique scratch file (`$TMPDIR/wb-<task>-<role>-<nonce>.txt`), post it with `bd comments add <id> -f <path>`, confirm the newest comment's first line, never reuse a scratch file, and never hand back in the same turn as the post, so a refused post comes back as `Full report: not posted` instead of a block that claims it posted. `task-verifier` stays without Write, and `wb:phase-verifier` now posts its report on the phase milestone too: since Claude Code refuses a multi-line quoted argument whose line starts with `#`, both post each record (report, Defect ledger, Test Integrity, phase verification) through the plugin's `wb-records` helper, as parts of at most 6 KB passed as escaped single-line arguments (`--escaped`; base64 only for bytes the escapes cannot express), followed by a manifest and a confirming `wb-records read`; a refused post returns those exact parts, which the coordinator may repost only verbatim through the same helper. Every reader uses `wb-records read`, and any status other than `ok` counts as missing. Allowing `wb-records` and `test-integrity` (see the README's Unattended runs) keeps an unattended run from stalling on prompts. A class fix's check passes the fixed test as `--test-file <path>=@esc:<escaped text>`.
  - **A test that claims to guard a criterion must fail on its break**: a planted defect that breaks the cited criterion fails a task (or blocks a checkpoint) when it survives a test that claims that criterion (its test-writer report names it, or it is the outer test), even when another plan test catches it. The fix worker either strengthens the test or, when another plan test is named, run, and shown catching the break, has `wb:test-writer` drop the test's guarding claim in a new report so it stands as a support test; the verifier records which. A survivor in a test that claims no guarding of the criterion is a follow-up. The always-FAIL list is unchanged.
  - **Tree fingerprints**: the coordinator records `test-integrity --fingerprint` immediately before and after every task verification, including the profile's dependency and build output directories (a new `build output dirs` profile key; the runner's defaults otherwise); a difference voids that verification and it runs again, and a fingerprint error fails closed. Each costs two full hashes of the tree per verification.
  - **Fewer waits**: before a phase (and in `create_tasks`), earlier plans' outer tests that this design's renames would break are found up front; a name-only one is planned as a rewrite task and the renaming task's verifier expects it, and any other is asked about before the phase. `/wb:create_design` asks, for each boundary, what the examples leave out (input nobody showed, a failure partway, other callers of what changes); each answer becomes a criterion, a case listed for your approval as left unhandled, or one that cannot happen. The prover lists what each stubbed service was assumed to accept, and the checkpoint report carries that list. An outer test whose class does not exist yet is committed red as it stands (a not-built red): no stub is written and nothing is asked. The worker notes the assertion failure it sees while building, and the verifier's planted defect for that criterion must be caught, so the assertion is still shown to fail. `/wb:update_status` skips its yes/no only when every transition moves forward and it writes nothing to beads, and never marks a plan complete while a milestone awaits your checks. implement suggests `/wb:testing-profile` when `.claude/wb/testing.md` is missing.
- **Rules and intents** (from two real runs that stalled for hours on narrowed wording: each stage had narrowed the intent a little and dropped its reason, and the next stage enforced the narrower words as a rule nobody chose). The new `plugin/docs/reference/rules-and-intents.md` is the one place authority, strength, the rule for changing an outer test, and the judge's limits are defined; other files link its clauses. Its evidence is incident-derived and weak (two runs, no external study), recorded in the file and as a dated Amendments line in the testing-guidance plan's README.
  - **One hard list**, stated once: workers never edit tests; red before green; an escalated integrity finding halts; every explicit verification and phase gate (missing or unparseable evidence, a failed verification, a production defect, a failed phase verification, the checkpoint, and no next phase before acceptance); safety and destructive actions; and your reserved decisions (a Goal or Non-goal change, retiring a criterion, accepting lost coverage, changing an outer test), each by name. Every plan line marked `strength: hard` holds literally too; only `strength: aim` lines may be judged by purpose.
  - **`create_project`** records each Intent line with why it exists, its source (your words verbatim from any of your messages, with the date, or "drafted from …" for agent wording), whether you reviewed it (`reviewed: yes | no`), and its strength. It asks one added question, "Which of these are hard limits rather than aims?"; a reply changes only the lines it addresses, and silence never erases your earlier words as a line's source.
  - **Older plans**: a line with no strength worded as a command (must, never, do not, only, required, always) is provisionally hard and is put to you for confirmation, never judged until then; a line protecting safety, data integrity, or honesty of evidence is hard; other unmarked lines are aims.
  - **`create_design`**: a metric or criterion checks its statement, never replaces it, and carries its why and strength; acceptance criteria gain `Guards against:` and `Strength:`, and a stricter line is marked `Narrows:`. The approval message lists every narrowing, quoted, under "Choices I made that tighten your intent", and approval covers only those. An unlisted narrowing found later is an aim, unless its source line is hard or it protects safety, data integrity, or honesty of evidence: then it stays hard and the missing listing is a design defect to correct. A Success statement can be amended when your direction contradicts it (a `Decide:` record and a README Amendments line).
  - **Hardness attaches to the purpose, never the mechanism**: a criterion's `Strength: hard` applies to its Guards against purpose; the mechanism a narrowing picks (a word list, a placement, an exact wording, a selector, a region) is always an aim, written `Strength: hard (purpose) / aim (mechanism)`, and any check serving the same purpose may replace it (an outer test's only as a rewrite proven to lose nothing). Narrowings in the approval message use all five lines of the form, quoting design.md verbatim.
  - **Proxy tests say so**: an outer test that checks a criterion through a word scan or a region exclusion names the criterion's Guards against and the proxy's known false hits in a comment and its report; word scans match whole words, scoped to the elements the criterion names.
  - **Acting within purpose**: when an aim's literal wording works against its purpose, the run acts within the purpose, posts a `judged:` record, and lists it under a new "Decisions I made for you" report section; never on the hard list, a hard line, a test, an assertion, or what a criterion means. A rule-based question quotes the rule, its source, and its purpose, and says whether the purpose is at stake. Tasks independent of a pending question keep running, independence defined exactly as for unattended continuation (outside its dependency closure both ways; no shared file, criterion, outer test, contract, or schema; doubt means dependent), with the checked task ids recorded.
  - **Outer tests**: the outer test is the plan's check of its criterion. What the criterion means is yours to decide; whether a changed test still checks it is a question evidence answers (see "Outer tests change on proof" above).
  - **Memories** carry their source: `user-stated` with your words verbatim, or `agent-derived`, which is an aim, never a rule.
  - `judged:` and `rewrite:` join every record-prefix list.
- **Not Run counts**: checkpoint reports and `validate_phase` show "Defect checks: N run, M survived, K not run (reasons)", so a check that could not run is visible instead of silent.
- **`create_research`, `create_design`, `create_tasks`** templates as described under Breaking; `create_project`'s design skeleton uses the new headings.
- **`validate_project`** is described as a repair tool for plan documents that look inconsistent, not a stage: `/wb:help`, the session orientation, and CLAUDE.md list it outside the stage chain.
- **`tdd-discipline`**: red means a failure caused by the behavior not being built yet (an assertion failure, or the code you are about to write not existing; a syntax error or a missing helper is not red), and the skill holds the single list of named exceptions (harness tasks with a can-fail proof, configuration, documentation, refactors under existing tests, build scripts).
- **`review-prep`** points to `/wb:test-audit` after the TDD check; `/wb:help` and the session orientation describe the new stages.

### Migration

The full guide is [docs/upgrading-to-5.md](docs/upgrading-to-5.md): what changes at each stage, plans in flight, new files, and what to expect in time and cost. In short:

1. `claude plugin update wb@gvarela-workbench` from your shell, then restart Claude (or `/reload-plugins`).
2. In-flight plans: keep running them as they are (no outer tests, see Breaking), or add Acceptance Criteria to design.md and re-run `/wb:create_tasks` if you want outer tests and `red(AC-n)` commits. Expect a `red(AC-n)` commit to appear mid-phase, before the task that implements the criterion.
3. Optional: run `/wb:testing-profile` once per repository to record your conventions and choices; `/wb:test-audit` and the reviewers read it. Without it, research and detection supply the stack.
4. Expect three Opus agents at each checkpoint (`wb:test-reviewer`, `wb:phase-verifier`, `wb:prover`), a test-writer spawn before each worker, and a Fable judge whenever the run would otherwise stop. `/wb:create_design` now runs as three passes and asks more; you can stop after any pass and resume. If a checkpoint holds, answer each numbered item by name.
5. A plan run on an earlier alpha may carry `delegation:`, `re-baseline:`, and `auto-continue:` records and `Sanctioned rewrite:` task lines. They are read as history; a `Sanctioned rewrite:` line still marks a rewrite task. Replies such as `delegate: test upkeep` and `sanction: R1` no longer do anything.
6. On a large repository, narrow the scope before running `/wb:test-audit`; the skill shows its estimate before it spends anything.
7. Replace `/wb:validate_execution <dir>` with `/wb:validate_phase <dir> all` (or `<dir> <phase>` for one phase) in scripts, handoffs, and notes; the old name no longer resolves.

### Evidence

- The `implement` and `implement_inline` flows were run headless on fixture projects, including a plan without acceptance criteria and two trap seeds (a missing module and a protected test that contradicts a criterion), both caught and halted at pre-flight with nothing committed.
- Cold audits ran on two real repositories, a mid-size Python service and a large Ruby on Rails application. On each, at least 8 of 10 sampled findings were real; a person spot-checked one sample and an AI verification checked the other. Against an earlier hand audit of the same repositories, the cold audits recovered 8 of 11 and 11 of 16 of its findings.
- An untriaged full audit cost about $28 on the first repository and about $99 on the second, which is why `/wb:test-audit` triages first and states a cost class before spawning.
- In blind trials on seeded defects, the 4.0.0 verifier already caught nearly all of them (24 of 24 clean diffs, 23 of 24 realistic ones); the one miss graded a defect "minor", which the never-minor boundary and `test-integrity` address.

- `create_research` and `create_product_research` completion summaries conditionally suggest `/wb:explore_design` — only when findings show multiple viable approaches.
- `validate_project` orphan detection exempts planning-prefix issues (`Q:`, `Decide:`, `Validate:`, `UI Q:`) — planning-phase records are intentionally not anchored in tasks.md frontmatter.
- Documentation sweep: the optional stage appears in every workflow rendering (help, CLAUDE.md, README, commands reference, workflow guide, generated project templates); help additionally documents `Decide:` lifecycle semantics (open = pending, closed = decided, rationale in close reason).

## [2.0.0] — 2026-07-31

The modernization release. One coordinated breaking change covering the Claude Code skills unification, the beads 1.0.2 CLI migration, and a repository restructure.

### ⚠️ Breaking / Requirements

- **Requires beads ≥ 1.0.2** (embedded-Dolt backend). The prompts now use `bd info`, `bd update --claim`, and auto-flush semantics; `bd sync` and `bd doctor` are gone from all guidance. **Update beads before updating the plugin** — old beads + new prompts will produce failing commands.
- **Repository layout changed**: the runtime plugin now lives in `plugin/`; installs cache only that subtree. If you reference repo paths directly (scripts, `--plugin-dir`), point at `plugin/`. All `/wb:*` command names are unchanged.
- **Workflow commands no longer auto-trigger**: the 13 `/wb:create_*`/`implement_*`/`validate_*`/`*_handoff`/`update_status` skills carry `disable-model-invocation` — you invoke them; Claude won't fire them spontaneously. Background discipline skills (tdd-discipline, verification-before-completion, status-sync, project-structure) are now Claude-only (hidden from the `/` menu).

### Changed

- All 14 workflow commands migrated from `commands/*.md` to canonical `skills/<name>/SKILL.md` form (skills/commands unification).
- Skill cores restructured for context economy: 8,439 → ~5,275 lines loaded at invocation (−37.5%); templates, sub-agent prompts, and reference material moved to on-demand supporting files with verified output parity (structural dry-run comparison + independent content-conservation audit).
- `implement_coordinated` workers are now a defined `task-worker` agent with the tdd-discipline skill preloaded; model selection moved from keyword regex to coordinator judgment with per-spawn overrides.
- Agents carry explicit `model:` selections (haiku for search, sonnet for analysis/verification) and `maxTurns` caps on search agents.
- Verification skills (`validate_execution`, `research-validation`) pinned to `model: sonnet` + `effort: high`.
- `status-sync` skill re-scoped to interactive deep-checks; the deterministic session-end reminder moved to a SessionEnd hook.

### Fixed

- `bd list` decision pipelines no longer silently truncate at 50 issues (`-n 0` added at 8 gating sites).
- Task claiming is atomic (`bd update --claim`) — closes the double-claim window in coordinated execution (14 sites).
- `validate_project` mode checks now use the same `git check-ignore` predicate as the SessionStart hook (the old tracked-file check false-warned before first commit).
- Phase-completion checks use the milestone's `blockedBy` (authoritative) instead of fragile title greps.
- Phantom barrier references removed from three sync summaries; two real pre-report gates added to the validation skills (validate_execution BARRIER 3, validate_project BARRIER 2).
- PostToolUse lint hook reads hook input from stdin JSON — it had been silently no-opping since Claude Code stopped setting `CLAUDE_TOOL_ARGS`.

- Workflow skills carry `allowed-tools: Read` — pre-approves file reads while the skill is active, so the on-demand supporting files (templates, sub-agent prompts, reference) load without permission prompts when your session is in a different project. Found in release testing; reads outside the active skill still follow your normal permission settings once the skill completes.

### Added

- `hooks/beads-drift-check.sh` (SessionEnd): one-line reminder when `.beads/` has uncommitted changes; silent when clean.
- `agents/task-worker.md`: focused single-task TDD worker for coordinated execution.
- `plugin/docs/reference/`: shared runtime docs (beads modes, documentarian philosophy, beads-not-initialized playbook) referenced by skills instead of duplicated in them.
- `displayName: Workbench` in the plugin manifest.

### Migration

1. Update beads first: `brew upgrade bd` (or equivalent) to ≥ 1.0.2, then in each beads project let it migrate (`bd info` to confirm; if it errors, `bd export` then `bd init --force --prefix <prefix>` then `bd import`).
2. `claude plugin update wb@gvarela-workbench` from your shell, then restart Claude (or `/reload-plugins`).
3. Nothing else changes day-to-day: same `/wb:*` names, same workflow sequence.
